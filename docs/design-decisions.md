# 设计决策记录

## D1. 为什么选「Go 引擎 + 原生壳」而不是 Flutter

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Flutter | UI 一份代码 | 平台能力仍要写 channel；单文件 20MB+ | 否 |
| React Native | 生态大 | 多一层 JS 运行时，包体更大 | 否 |
| **Go + 原生** | 业务一份、平台能力全原生、Linux 可测 | UI 写两遍 | **是** |
| 纯双端原生 | 最可控 | 业务写两遍，接口会漂移 | 否 |

关键论据：本项目的复杂度集中在「各平台登录态如何拿到、接口如何调」，这部分与 UI 无关，
且最容易因平台改版失效——必须**只写一份**并且能独立测试。

## D2. 为什么 iOS 不用「塞个 Go 二进制用子进程跑」

iOS 沙盒禁止执行外部可执行文件（代码签名 + 沙盒双重限制）。必须用 `gomobile bind`
编成静态库，由 Swift 在**同一进程内**调用。Android 两种都行，为保持一致也用 bind。

## D3. 为什么面板用内嵌 HTTP 而不是纯原生 UI

1. 双端 UI 只写一份，改版成本最低；
2. 壳层保持极薄，平台差异压缩到最小；
3. 面板 HTML 零外部依赖（无 CDN），离线可用，首屏 < 5KB；
4. 未来要换原生 UI，直接调 `mobile.go` 的 JSON 接口，引擎不动。

## D4. 为什么签到必须串行

桌面版经验（逆向结论）：同一设备短时间批量请求是触发风控的首要原因。
引擎内 `CheckinAll` 固定串行 + 1.2s 间隔；同平台多账号由 `scheduler` 保证 ≥10 分钟错峰。

## D5. 为什么 iOS 后台定时不可靠

`BGTaskScheduler` 只保证「大致时机」，且用户不常打开 App 就几乎不触发。
产品上必须降级为「到点本地通知 + 打开即补签」，不能承诺准时。

## D6. 接口字段为什么要多重兜底

逆向只能拿到接口形状（路径、方法、请求头），拿不到真实响应结构。
所以字段解析一律 `firstOf(...)` 多候选 + 类型宽松转换，宁可降级不可 panic。
等拿到真实响应后，用 `docs/platform-notes.md` 记录确认结果并收窄候选。

## D7. 错误信息为什么在 httpx 层做语义化

网关层（APISIX/OpenResty）鉴权失败返回 HTML 而非 JSON。若直接透传，用户看到的是
一大段 HTML。所以在 `JSON()` 里按状态码给出中文语义（401 → 凭据失效，5xx → 服务端异常）。
