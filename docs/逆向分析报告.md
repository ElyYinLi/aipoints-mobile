> 目标：`AI积分助手-免安装-v2.2.0-Windows.zip`（55.6 MB，2026-11-03 构建）
> 分析环境：Linux x64 沙箱，静态分析为主，未运行目标程序
> 分析日期：2026-11-17

## 一、先回答你的三个问题

### 1）加密了吗？—— 没有。**没有加壳、没有混淆、没有授权校验**

| 检查项 | 结果 | 依据 |
|---|---|---|
| 打包方式 | PyInstaller 6.x（onedir 模式） | `AiPointsAssistant.exe` 内含 `MEIPASS` / `pyi-*` 引导模块 |
| 运行时 | CPython **3.14**（`python314.dll`） | 解包头部标识 `Python version: 3.14` |
| 代码混淆 | 无 PyArmor、无 Nuitka、无 VMProtect/ Themida | 包内无 `pyarmor_runtime`、无 `.pyd` 形式的业务模块 |
| 字节码状态 | **完整可读**，45 个业务模块全部解出 | 解包后 `PYZ.pyz_extracted/app/**` 共 45 个 `.pyc`、1295 个代码对象 |
| 授权/激活 | 无任何 license、机器码、在线校验逻辑 | 全量域名扫描只命中官方平台与 Chromium 下载源 |
| 网络回传 | **零**：无自建服务器、无统计上报 | 见第四节域名清单 |

唯一的"加密"是**它去解别人的密文**：程序里手写了一份 AES-256-GCM（`app/aes_gcm.py`，逐字节照 FIPS-197 实现），用来解开 Chrome/Chromium 的 `v10` cookie 密文，以及 WorkBuddy 客户端里被 AES-GCM 信封包起来的 `accessToken`。换句话说：

> 程序本身是敞开可读的，真正有防护的是**它要读取的那七家客户端**。

### 2）它到底怎么实现的？—— 一套"登录态收割 + 官方接口直连 + 浏览器代打"的组合拳

三种技术路线并存，按平台难度取舍：

| 路线 | 适用平台 | 做法 |
|---|---|---|
| **A. 接口直连** | WorkBuddy、Trae、Qoder、MiniMax、百度搭子、灵犀 | 拿到 token/cookie 后直接调官方接口，毫秒级 |
| **B. 浏览器代打（CDP）** | 豆包、Trae 换票、各平台首次登录 | 起一个真实 Chromium，用 DevTools 协议驱动页面，让页面自己发请求（风控参数由页面算） |
| **C. 本机凭据收割** | WorkBuddy、Qoder、MiniMax、Trae、灵犀、百度搭子 | 读桌面客户端本地登录态；遇到加密就解密，遇到密钥只在内存就**扫客户端进程内存**找 |

### 3）移动端能不能做？—— 7 家里 **5 家能做、1 家有条件、1 家基本做不了**

| 平台 | 移动端可行性 | 核心障碍 |
|---|---|---|
| WorkBuddy（CodeBuddy） | **可行** | 有官方浏览器 OAuth（state + authUrl + 轮询取票），手机端一样能走 |
| Trae | **可行** | 登录态是 httpOnly cookie，WebView 登录后原生层直接带 cookie 取 JWT |
| MiniMax Code | **可行** | 支持 Device Authorization 授权码流程；签名头是"固定盐 + md5"，可复刻 |
| 百度搭子（DuMate） | **可行** | 百度账号 cookie + 纯 REST 接口 |
| 灵犀（WPS） | **可行** | 金山文档 cookie + 纯 REST 接口 |
| 豆包 | **有条件** | 必须伪装 UA（`SamanthaDoubao`）并在 WebView 里点页面元素，能跑但很脆弱 |
| Qoder | **基本不行** | 领取必须带 `Cosy-Machine*` 指纹，而指纹由桌面端 `runtime-info.exe` 实时生成，伪造直接 `503 RISK_DEPENDENCY_UNAVAILABLE` |

**还有一条比技术更硬的限制**：iOS 不给你"每天 10:00 准时在后台跑一次"的能力（`BGTaskScheduler` 只保证"大致时机"，且用户不常开 App 就基本不触发）。Android 可以用 `WorkManager` + 精确闹钟。所以**"定时自动签到"这个卖点在 iOS 上只能降级成"打开即补签 + 本地通知提醒"**。

## 二、证据与方法（Observed）

### 2.1 解开过程

```
PyInstaller CArchive → main.pyc + PYZ.pyz（241 个模块）
PYZ 解包 → 45 个业务模块（app/）+ 标准库 + PySide6/cryptography 第三方库
Python 3.14 字节码 → 自建 CPython 3.14 解释器加载 → 反汇编 + 常量/文档字符串提取
```

说明：Python 3.14 目前**没有成熟的一键反编译器**（pycdc/uncompyle6 均不支持）。我改用「自建 3.14 解释器 + 反汇编 + 文档字符串还原」的方式做符号级还原。结果比想象中好得多——**作者给几乎每个函数都写了中文文档字符串，等于自带一份设计说明书**（共 839 + 1853 + 640 行有效说明）。所以本报告里的"设计意图"部分是**有原文依据的**，不是猜的。

### 2.2 代码规模

| 指标 | 数值 |
|---|---|
| 业务模块 | 45 个 |
| 代码对象（函数/类体） | 1295 个 |
| 字节码指令数 | ≈ 24.4 万（约合 3–4 万行 Python） |
| 第三方依赖 | 仅 PySide6（Qt6 UI）+ cryptography（Qoder 用），其余全标准库 |
| 分发体积 | exe 2.85 MB + `_internal` 131 MB（大头是 Qt 与 Chromium 安装器逻辑） |

值得注意：连 AES-GCM 都是**自己手写**的（`app/aes_gcm.py`，注释写"逐字节照 FIPS-197 写、不追求速度"），目的就是打包时不带第三方加密库。

### 2.3 模块地图

```

├── env_setup.py         内置 Chromium 下载安装（约 196 MB，双镜像）
├── providers/
│   ├── base.py          Provider 抽象：query / checkin / scan_local / bonus_*

│   ├── qoder_*          Qoder
│   ├── minimax_*        MiniMax Code
│   ├── dumate_*         百度搭子（含好运充能站抽奖）
│   ├── lingxi_*         金山灵犀

└── ui/                  PySide6 界面：无边框窗口、托盘、卡片、设置、主题
```

## 三、七家平台的接入细节（Observed）

> 下表全部来自字节码常量与作者文档字符串，可直接作为移动端实现的接口清单。

### 3.1 WorkBuddy（CodeBuddy）

| 项 | 内容 |
|---|---|
| 凭据来源 | ① 本机客户端登录态文件（`auth` 目录，`accessToken` 是 AES-256-GCM 信封）；② 官方浏览器 OAuth（`/v2/plugin/auth/state` → authUrl → 轮询 `/v2/plugin/auth/token`）；③ `refresh_token` 续期（服务端轮换） |
| 读签到状态 | `POST https://{domain}/v2/billing/meter/checkin-activity-status` |
| 签到 | `POST https://{domain}/v2/billing/meter/daily-checkin`，body `{}` |
| 余额（App 首屏口径） | `POST https://{domain}/billing/meter/get-user-resource-summary`（**注意：网关路由不带 `/v2`**），取 `data.Packages[].CycleRemainCapacity` 求和 |
| 猫猫旅行 | `GET /activity/growth/buddy/travel/status`、`/config`；`POST /travel/depart`（body `{"location_id":N}`）、`/travel/claim`（body `{}`），走 `www.workbuddy.cn` |
| 请求头 | `Authorization: Bearer`、`X-User-Id`、`X-Enterprise-Id`、`X-Tenant-Id`、`Origin/Referer/User-Agent`（余额接口缺浏览器三件套头会 **403**） |
| 设备指纹 | 无（作者注释明确"仅需 Bearer Token，无需 Turing Shield"） |
| 加密细节 | 密钥 `atRestSecretKey`（44 字符 base64）**只驻留客户端进程内存**，磁盘上没有；程序用 `SHA256(secret)` 派生 key、`SHA256(key)[:16]` 作 keyId，再解 AES-GCM 信封。找不到就扫 `WorkBuddy.exe` 进程内存（实测约 16 秒） |

### 3.2 Trae

| 项 | 内容 |
|---|---|
| 凭据来源 | 各账号独立浏览器 profile 里的 httpOnly cookie → 用 CDP 让页面自己调 `https://api.trae.cn/cloudide/api/v3/common/GetUserToken` 换 JWT（JS 读不到 httpOnly，只能代发） |
| 签到状态 / 签到 | `GET/POST https://api.trae.cn/trae/api/v2/ug/checkin_credits/status`、`/claim` |
| 余额 | `GET https://api.trae.cn/trae/api/v2/pay/web_user_ent_usage`、`/trae/api/v2/ug/activity/info` |
| 设备指纹 | `x-device-id` / `x-device-brand` / `x-device-type`。官方只认"任意 15 位数字"，所以程序给每个账号单独生成一个（一号一天一名额） |
| 坑 | 浏览器 fetch 带这三个头会触发 CORS 预检失败（`code=9004`），必须原生层直发；`checked_in`（账号维度）与 `did_checked_in`（设备维度）要分开读，或起来会"假绿" |

### 3.3 Qoder

| 项 | 内容 |
|---|---|
| 凭据来源 | 本机客户端 `auth.v1.dat` 或 `state.vscdb` 的 `secret://aicoding.auth.userInfo`，均为 Chromium OSCrypt（`v10` + AES-256-GCM，密钥取自同目录 `Local State`，Windows 走 DPAPI） |
| 领取主链路 | `GET https://openapi.qoder.com.cn/sash/api/v1/me/campaigns` → `POST /sash/api/v1/me/campaigns/{campaignId}/claim` |
| 余额 | `GET /api/v2/quota/usage`、`/api/v1/userinfo` |
| 刷新 | `POST /api/v1/deviceToken/refresh`，body `{"refresh_token":"drt-…"}` |
| 设备指纹 | **硬门槛**：`Cosy-ClientType:10`、`Cosy-Version:0.3.3`、`Cosy-MachineOS`、`Cosy-MachineToken`、`Cosy-MachineCode`、`Cosy-MachineType`、`Cosy-MachineId`，由 `<Qoder安装目录>\resources\umid\runtime-info.exe` 实时生成（`echo {"account":"…"} | runtime-info.exe <串> --account-stdin`）。不带 → 服务端返回**空列表**；伪造 → **503 RISK_DEPENDENCY_UNAVAILABLE** |
| 域名选择 | QoderCN 新版 → `openapi.qoder.com.cn`；其余 → `openapi.qoder.sh`（选错必然 401） |

### 3.4 MiniMax Code（海螺）

| 项 | 内容 |
|---|---|
| 凭据来源 | 本机客户端 token；或 **Device Authorization**（`start_device_authorization` + `_poll_device_token`）；或浏览器登录 |
| 签到面板 / 领取 | `GET {host}/minimax-cloud/api/v1/signin/status`、`POST {host}/minimax-cloud/api/v1/signin/claim` |
| 续期 | `POST {account}/oauth2/token` |
| 签名头 | `yy` = `md5(encodeURIComponent(path) + "_" + body + "_" + md5(str(ms)) + SIGN_SUFFIX)`；`x-timestamp` = 秒；`x-signature` = `md5(sec + SIGN_SALT + body)`。**固定盐 + md5，纯算法，移动端可完全复刻** |
| UA | `MiniMaxAgent Mozilla/5.0 (Windows NT 10.0; Win64; x64) … MiniMax/3.1.0 Chrome/148…`（客户端标识写在 UA 里） |
| 区域 | `agent.minimax.cn` / `agent.minimax.io`（账号与地区绑定，选错 401） |

### 3.5 百度搭子（DuMate）

| 项 | 内容 |
|---|---|
| 凭据来源 | 百度账号 cookie（本机客户端 Chromium 库解密，或 CDP 扫码登录采集） |
| 接口 | `GET /api/dumate/points/loginBonusInfo`、`POST /api/dumate/points/loginBonus`、`GET /api/dumate/points/quota_overview`、`GET/POST /api/dumate/activity/growth-plan/draw[/status]`（写接口要 `x-bce-request-id`） |
| 备注 | 程序是从 `totorosir-dumate-checkin v1.1.0` 移植的，注释里写明了出处 |

### 3.6 灵犀（金山 WPS）

| 项 | 内容 |
|---|---|
| 凭据来源 | `kdocs.cn` cookie（同百度搭子两条路） |
| 接口 | `GET /api/public/v1/tasks`（任务与签到状态）、`POST /api/public/v1/tasks/daily_check_in/claim?date=YYYY-MM-DD`、`GET /api/public/v1/credits/balance` |
| 规则 | 签到规则**全部由接口给**（`type=daily` 那项的 `extra.check_in_days` 是本周期每天状态，`available` 才能领），本地不写死奖励数额 |

### 3.7 豆包

| 项 | 内容 |
|---|---|
| 路线 | **不直连接口**。用带 `SamanthaDoubao/2.33.5` 标识的 UA 拉起 Chromium，打开活动页，再用 CDP 找"每日签到"卡片、按状态点那一下 |
| 为什么 | 活动页那句"仅支持豆包电脑版"是前端按 `navigator.userAgent` 里有没有 `samantha doubao` 判的（i18n key `DBPC_BTS_Ineligible_NonPC_Title`）。带上这串，闸门整块消失 |
| 接口 | `POST /alice/ug/campaign/landing/checkin`（由页面自己发，`scene`、`AgwCommonParam`、风控 token 都是页面算的） |
| 额外逻辑 | 签完还要扫进度条上"已解锁的档位奖励"逐个领取 |

## 四、安全性评估

**做得对的地方**

- 全量域名扫描结果只有官方平台 + Chromium 下载镜像，**没有任何自建服务器或统计上报**：「登录态全部留在本机」这句宣传是真的：

```
www.doubao.com · api.trae.cn · work.trae.cn · openapi.qoder.com.cn · openapi.qoder.sh
qoder.cn · agent.minimax.cn/.io · account.minimax.cn/.io · dumate.baidu.com
www.baidu.com · lingxi.kdocs.cn · www.workbuddy.cn
cdn.playwright.dev · cdn.npmmirror.com   ← 仅用于下载内置 Chromium
```

- 日志做了脱敏约定（注释多次强调 cookie/token 不落日志）。
- 读取客户端 cookie 用"拷一份到临时目录只读打开"，不碰原库。

**需要指出的问题**

| 问题 | 说明 | 严重度 |
|---|---|---|
| 凭据明文落盘 | `accounts/<tool>.json` 里的 `cred`（cookie / token）是**明文 JSON**，未做任何本地加密。同用户权限下的任何进程都能读走 → 等价于账号接管 | 高（自家产品一定要改） |
| 扫进程内存取密钥 | WorkBuddy 5.6.2 的 `atRestSecretKey` 只在内存，程序靠扫 `WorkBuddy.exe` 可读内存段 + 校验 keyId 来找。技术上很漂亮，但这是**绕过他人客户端凭据保护**的行为 | 高（合规风险） |
| 自动化签到本身 | 各家签到/抽奖活动条款普遍禁止脚本化，账号有被风控/封禁风险 | 中高 |
| 无完整性校验 | 程序不校验自身，任何人改两行字节码就能重打包（也就意味着你不能靠"加壳"保护你自己的移动端） | 中 |

## 五、移动端方案（Inference）

### 5.1 能复用什么、必须重写什么

| 能力 | 桌面版做法 | 移动端对应做法 |
|---|---|---|
| 登录态获取 | 读桌面客户端本地文件 / 扫内存 | **不可移植**。改为各家网页/授权登录，在 App 内的隔离 WebView 里完成 |
| 多账号隔离 | 每个账号一个 Chromium profile 目录 | iOS：每账号一个 `WKWebsiteDataStore`；Android：每账号独立 `CookieManager` 实例 + 独立 WebView 进程 |
| 定时签到 | QTimer 30s 轮询 + 随机排期 | Android：`WorkManager` + `AlarmManager.setExactAndAllowWhileIdle`；iOS：`BGTaskScheduler`（不保证时刻）+ 打开即补签 |
| 接口直连 | urllib | 原生 `URLSession` / `OkHttp`（**不要在 WebView 里发**，会撞 CORS，Trae 就是这么踩的） |
| 豆包 | 隐藏 Chromium + CDP | 隐藏 `WKWebView`/`WebView` + `evaluateJavaScript` 点击；UA 用 `customUserAgent` 覆盖 |
| 凭据存储 | 明文 JSON | Keychain（iOS）/ Keystore + EncryptedSharedPreferences（Android）；绝不明文 |
| Qoder | runtime-info.exe | **无解**，只能降级为"展示余额 + 跳转官方 App 手动领" |

### 5.2 建议的技术选型

- **跨端一套**：Flutter + `webview_flutter`（自定义 UA、cookie 注入、JS 求值都够用）+ `flutter_secure_storage` + `sqflite`。7 家平台全是 HTTP + WebView，没有重算法，Flutter 完全够。
- **要更稳的双端原生**：SwiftUI + WKWebView / Kotlin + Compose + WebView。iOS 的 `WKHTTPCookieStore` 比 Flutter 插件更可控，如果你把豆包和 Trae 当核心功能，建议原生。
- **不要做的事**：不要做一个"后端代签"服务——那等于把用户凭据集中到你服务器，风险和合规成本都爆炸。

### 5.3 建议的最小可行版本（MVP）

1. **第一批做 3 家**：WorkBuddy（OAuth 最规范，最好做）+ 灵犀 + 百度搭子（两家纯 cookie + REST，一天能通）。
2. **第二步加 Trae**（设备头 15 位数字自己生成，难点只在 httpOnly cookie 取 JWT）。
3. **第三步 MiniMax**（签名可复刻，注意 CN/国际区域）。
4. **豆包放最后**：DOM 选择器随官方改版就崩，维护成本高。
5. **Qoder 直接不做领取**，只做"余额展示 / 一键跳转"。

### 5.4 必须提前想清楚的三件事

1. **iOS 上"定时自动签到"做不到准时**。产品文案要提前改成"到点提醒 + 打开即补签"，否则用户会判定为 bug。
2. **上架风险很高**。Apple 审核指南 5.2.1/5.2.2（使用第三方服务/内容）与 Google Play 的"自动化奖励"条款都可能直接拒。现实路径是：TestFlight 内测 / 企业签名 / Android 侧载。
3. **别把桌面版的"扫内存取密钥"搬到移动端**——移动端没有这个场景，也不该有。

## 六、未解决 / 需要你确认的事项

| # | 事项 | 为什么没结论 |
|---|---|---|
| 1 | 各家接口在**真实账号**下的实际返回，尤其是风控触发阈值 | 我不能也不应该代你登录，静态分析只能到"接口长什么样" |
| 2 | MiniMax 的 `SIGN_SALT` / `SIGN_SUFFIX` 具体值 | 常量在混淆过的字符串表里，需要动态验证（拿一个真 token 打一次接口即可反推） |
| 3 | 豆包的 DOM 选择器稳定性 | 依赖活动页当前版本，官方改版就失效（作者自己在更新日志里也承认） |
| 4 | Qoder 是否有移动端可用的指纹替代方案 | 目前只看到桌面 `runtime-info.exe`，除非官方开放移动端 SDK |
| 5 | 是否需要我把某个 Provider 的字节码**还原成可读 Python 源码** | 3.14 无成熟反编译器，我可以按函数逐个手工还原（比如 WorkBuddy 的授权链路），但那是另一个工作量级 |

## 七、一句话总结

**这程序没加密，代码写得相当规整（自带中文设计文档），技术上就是"把七家 AI 工具的签到接口用统一模型包起来"。你完全有能力做一个移动端版本——真正卡住你的不是逆向难度，而是三件事：桌面登录态在手机上拿不到、Qoder 的桌面指纹无法替代、iOS 不给后台定时权限。把这三条绕开（换登录方式、砍掉 Qoder 领取、iOS 改成提醒+补签），产品就成立。**

> 合规提示：逆向分析用于自用/学习没问题；但如果要把"绕过第三方风控、读取他人客户端凭据"的做法做成对外分发的产品，涉及各平台用户协议与《反不正当竞争法》风险，建议只保留"用户授权自己的账号、走官方登录"的部分。
